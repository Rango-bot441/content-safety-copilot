# 用户研究：Content Safety Copilot

## 1. 研究目标

本项目聚焦一个具体问题：创作者在内容发布前，如何更低成本地发现风险表达，并获得可执行的修改建议。

研究目标：

- 明确目标用户是谁。
- 梳理创作者发布前的真实痛点。
- 找到内容安全工具需要解决的关键任务。
- 为 PRD 的功能范围、优先级和指标设计提供依据。

## 2. 目标用户画像

### 2.1 中腰部创作者

| 维度 | 描述 |
| --- | --- |
| 账号阶段 | 已经有稳定内容方向，但增长不稳定 |
| 典型垂类 | 职场、教育、财经、健康、泛知识、本地生活 |
| 核心目标 | 提升内容发布效率，减少违规和限流风险 |
| 主要痛点 | 知道要“合规”，但不知道具体哪些表达有风险 |
| 产品诉求 | 快速指出风险点，并给出能直接使用的替代表达 |

典型场景：

```text
创作者写好标题和脚本
  → 担心表达太绝对或评论引导不合适
  → 希望发布前快速检查
  → 根据建议修改后再发布
```

### 2.2 内容运营人员

| 维度 | 描述 |
| --- | --- |
| 工作内容 | 帮创作者看选题、脚本、标题、评论互动 |
| 核心目标 | 提高内容初审效率，减少重复沟通 |
| 主要痛点 | 每条内容都人工判断，沟通成本高 |
| 产品诉求 | 快速定位风险类型，并形成统一修改口径 |

典型场景：

```text
运营收到多位创作者脚本
  → 先用工具做初筛
  → 标记高风险表达
  → 将修改建议发给创作者
```

### 2.3 MCN / 内容团队负责人

| 维度 | 描述 |
| --- | --- |
| 工作内容 | 管理多个账号和内容生产流程 |
| 核心目标 | 降低团队内容安全事故概率 |
| 主要痛点 | 不同运营对风险表达理解不一致 |
| 产品诉求 | 建立标准化审核规则和发布前检查流程 |

典型场景：

```text
团队准备批量发布内容
  → 先用统一规则初筛
  → 高风险内容进入人工复核
  → 低风险内容进入发布排期
```

## 3. 用户痛点

| 痛点 | 具体表现 | 产品机会 |
| --- | --- | --- |
| 风险识别不确定 | 创作者不清楚“哪些词危险” | 用规则和示例明确风险表达 |
| 平台提示不可执行 | 只知道有问题，不知道怎么改 | 给出风险原因和替代表达 |
| 高敏垂类压力大 | 财经、健康、教育内容边界难判断 | 建立垂类风险类型和自查清单 |
| 审核沟通成本高 | 运营反复解释同类问题 | 输出统一的修改建议 |
| 内容吸引力与安全冲突 | 改得太保守会失去标题吸引力 | 改写时保留原意和表达强度 |

## 4. 关键用户任务

| 用户任务 | 重要性 | 当前 MVP 覆盖方式 |
| --- | --- | --- |
| 发布前快速检查标题和脚本 | 高 | 内容送检表单 |
| 找到具体风险表达 | 高 | 命中风险点列表 |
| 理解为什么有风险 | 高 | 风险原因说明 |
| 获得可复制的改写结果 | 高 | 修改前后对比 + 一键复制 |
| 发布前做最后确认 | 中 | 自查清单 |
| 团队沉淀规则 | 中 | 后续规则库配置 |
| 跟踪发布后效果 | 中 | 后续数据反馈与指标看板 |

## 5. 用户旅程

```text
创作完成
  → 产生发布焦虑：担心违规、限流、被举报
  → 打开 Content Safety Copilot
  → 输入垂类、标题、脚本、评论引导
  → 查看风险等级和可发布分
  → 根据风险解释理解问题
  → 使用改写建议修改内容
  → 复制修改后文案
  → 按自查清单确认
  → 回到发布流程
```

## 6. 核心洞察

### 洞察 1：创作者需要的是“改法”，不是“判罚”

只提示“内容有风险”会让创作者停在问题层面。更有价值的是把风险翻译成具体修改动作。

### 洞察 2：内容安全不应牺牲表达吸引力

创作者关心内容能不能发，也关心改完以后还有没有吸引力。因此改写建议要保留原意，而不是简单删掉所有强表达。

### 洞察 3：高敏垂类需要边界说明

财经、健康、教育、就业等内容不一定不能讲，但必须避免确定性承诺，并补充适用条件和信息边界。

### 洞察 4：发布前自查能降低“最后一步失误”

即使系统已经给出建议，创作者仍需要人工确认事实来源、适用范围和互动方式。自查清单可以帮助用户建立稳定习惯。

## 7. 对产品设计的影响

| 研究结论 | 产品设计响应 |
| --- | --- |
| 用户需要快速定位问题 | 首页直接展示输入区和检测结果，不做复杂导航 |
| 用户需要知道为什么 | 每个风险点必须配风险原因 |
| 用户需要能直接修改 | 提供修改前后对比和一键复制 |
| 用户担心改完没吸引力 | 改写原则保留原意，不做过度保守表达 |
| 用户需要发布前确认 | 检测结果下方保留自查清单 |
